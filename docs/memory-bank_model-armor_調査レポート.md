# Google Cloud Agent Platform における Memory Bank / Model Armor 調査レポート

作成日: 2026-08-16
主な情報源: Google Cloud 公式ドキュメント(docs.cloud.google.com)、Google Cloud 公式ブログ、国内技術ブログ

---

## 0. 前提知識: Agent Platform とは

- 正式名称は **Gemini Enterprise Agent Platform**(旧称: Vertex AI Agent Engine / Agent Builder)。Google Cloud 上で AI エージェントを「構築(Build)→スケール(Scale)→ガバナンス(Govern)→最適化(Optimize)」するためのフルマネージド プラットフォーム。
- 主な構成要素:
  - **Agent Development Kit (ADK)**: エージェント実装用の OSS フレームワーク。LangChain / LangGraph / LlamaIndex / AG2 / CrewAI などのサードパーティ フレームワークやカスタム実装もサポート。
  - **Agent Runtime**: エージェントをサーバーレスでデプロイ・スケールするマネージド実行環境。
  - **Sessions(セッション)**: ユーザーとエージェント間の 1 回の会話(メッセージ・アクションの時系列 = SessionEvents)を保持する「短期記憶」。
  - **Memory Bank**: セッションを横断する「長期記憶」を生成・保存・取得するサービス(本レポートの対象①)。
  - **Agent Gateway**: エージェントへのトラフィックを集約管理するゲートウェイ。ここに **Model Armor**(本レポートの対象②)を組み込み、入出力の検査を行える。
  - その他: Example Store、Evaluation Service、Sandbox(コード実行)、Agent Registry など。
- 位置づけの整理:
  - Memory Bank = 「スケール(Scale)」領域のコンテキスト管理サービス。
  - Model Armor = Security Command Center 系のセキュリティ サービスで、Agent Platform には Agent Gateway 経由や API 直接呼び出しで統合する。

### 押さえておきたい基本用語

| 用語 | 意味 |
|---|---|
| セッション(短期記憶) | 1 会話内の履歴。会話が終われば通常は次の会話に引き継がれない |
| 長期記憶(Long-term Memory) | ユーザーの好み・属性などをセッション横断で保持する情報 |
| メモリのスコープ(scope) | 記憶を分離するキー(例: user ID + agent 名)。ユーザーごとのデータ分離を実現 |
| プロンプト インジェクション | 入力に不正な指示を紛れ込ませ、モデルに意図しない動作をさせる攻撃 |
| ジェイルブレイク | モデルの安全ガードレールを回避させる攻撃 |
| メモリ ポイズニング | 誤情報・悪意ある情報を長期記憶に混入させ、以降のセッションの挙動を汚染する攻撃 |
| サニタイズ | プロンプト/レスポンスを検査し、問題部分をブロック・マスキングする処理 |

## 1. Memory Bank

### 1.1 概要

- ユーザーとエージェントの会話をもとに**長期記憶を LLM で動的に生成・管理するフルマネージド サービス**。
- ステートレスなエージェントに「ユーザーごとの記憶」を持たせ、**セッションをまたいだパーソナライズと会話の継続性**を実現する。
- 各記憶は次のような JSON で表現される、独立した自己完結型の「事実(fact)」:

```json
{
  "name": "projects/.../reasoningEngines/.../memories/...",
  "scope": { "agent_name": "My agent", "user": "my user ID" },
  "fact": "ユーザーは○○を好む"
}
```

- 技術的背景として、Google 研究チームの **Reflective Memory Management (RMM)** というフレームワークに基づくとされる(会話ログの丸ごと保存ではなく、意味のある情報の抽出と既存記憶との統合を行う点が特徴)。
- 生成 AI 機能であるため、生成 AI サービス固有の規約が適用される点に注意。

### 1.2 主要機能

**(1) 記憶の生成(Memory Generation)**
- 記憶の抽出(Extraction): 会話などのソースデータから意味のある情報だけを LLM が抽出して永続化。
- 記憶の統合(Consolidation): 新しい情報を既存記憶と突き合わせ、矛盾解消・重複排除しながら記憶を進化(作成・更新・削除)させる。エージェントや人間が事前抽出した記憶を統合することも可能。
- 非同期生成: 記憶生成はバックグラウンドで実行され、エージェントは生成完了を待つ必要がない(応答レイテンシに影響しない)。
- 継続的なイベント取り込み: 会話イベントをストリーミングで取り込み、バッチ処理ルールに従って記憶生成を自動トリガー。
- カスタマイズ可能な抽出: 「トピック」と few-shot 例を指定し、何を意味のある情報とみなすかを構成できる。
- マルチモーダル理解: マルチモーダル情報を処理し、テキストのインサイトとして保持。

**(2) マネージド ストレージと取得**
- スコープ(ID)単位のデータ分離: 記憶の統合・取得は特定の ID に分離される。
- 永続的でアクセス可能なストレージ: Agent Runtime 上だけでなく、ローカル環境や他のデプロイ先からも利用可能。
- 類似性検索(Similarity Search): 現在の会話に関連する記憶だけをスコープ内で検索して取得。全件取得(Get/List)も可能で、開発・デバッグに有用。
- 自動有効期限(TTL): 記憶に TTL を設定し、古い情報を自動削除。インスタンス レベルで自動適用の構成も可能。
- 記憶のリビジョン: 記憶が新情報でどう変化したかの履歴を自動で保持・確認できる。
- 制限付き権限: IAM Conditions で、特定スコープの記憶を読み書きできるプリンシパルを制限。

**(3) エージェント統合**
- ADK 統合: 組み込みツールと `VertexAiMemoryBankService` により、ADK エージェントが Memory Bank の読み書きを自動オーケストレート。
- 他フレームワーク: Memory Bank の呼び出しをツールやコールバックとしてラップして利用。

### 1.3 動作フロー(Sessions との連携)

1. `CreateSession`: 会話開始時にセッション作成(ユーザー ID 必須)。
2. `AppendEvent`: ユーザー発話・エージェント応答・ツール実行などのイベントをセッションに追記。
3. `ListEvents`: エージェントが会話履歴を取得。
4. 記憶の生成:
   - `GenerateMemories`: セッション終了時やターン終了時などのタイミングで、会話履歴から事実を自動抽出。
   - `CreateMemory`: エージェントが記憶を直接書き込む(記憶をツールとして扱い、何を保存するかをエージェント側で制御)。
5. `RetrieveMemories`: 以降のやり取りで記憶を取得(単純取得 or 類似性検索)し、プロンプトに挿入。

### 1.4 ユースケース

- **長期的なパーソナライズ**: 例)過去のサポート チケットや商品の好みを覚えていて、再質問が不要なカスタマーサービス エージェント。
- **LLM による知識抽出**: 例)技術論文群を読み、主要な発見・手法・結論を統合した記憶を構築するリサーチ エージェント。
- **動的で進化するコンテキスト**: RAG が静的な外部ナレッジベースを参照するのに対し、Memory Bank はエージェント発の新情報を継続的に統合し、記憶を更新し続ける(RAG との明確な違い・補完関係)。

### 1.5 エンタープライズ セキュリティ / 運用面

- VPC Service Controls、CMEK(顧客管理暗号鍵)、データ所在地(保存時)、HIPAA、アクセスの透明性・アクセス承認に対応(Agent Platform のサービス別対応表より)。
- 記憶生成の ML 処理は、構成したモデル エンドポイントのリージョン/マルチリージョン内で実行。
- **メモリ ポイズニングのリスク**: 誤情報が記憶に保存されると、以降のセッションでエージェントがそれに基づいて動作する恐れがある。公式ドキュメントの推奨緩和策:
  - **Model Armor** で Memory Bank に出入りするプロンプトを検査する(2 サービスの直接的な接点)。
  - 敵対的テスト(レッドチーム演習)。
  - サンドボックス実行 + 厳格なアクセス制御・人間によるレビュー。

### 1.6 導入方法

- REST API クイックスタート(Sessions / Memory Bank API を直接呼ぶ)と ADK クイックスタート(ADK にオーケストレーションを任せる)が用意されている。
- Terraform でのプロビジョニングや、コンソールからの管理も可能。

## 2. Model Armor

### 2.1 概要

- **LLM のプロンプトとレスポンスを送信前/提示前にスクリーニングする、モデル非依存のフルマネージド セキュリティ サービス**。Security Command Center ファミリーの一部(スタンドアロン利用も可能)。
- 目的: 悪意ある入力の防御、コンテンツ安全性の検証、機密データ保護、コンプライアンス維持、多様な AI 環境全体での安全性・セキュリティ ポリシーの一貫適用。
- **モデル・クラウド非依存**: Google のモデルに限らず、REST API 経由で任意の AI アプリ(マルチクラウド/オンプレ含む)に組み込める。

### 2.2 アーキテクチャ(データフロー)

1. ユーザーがアプリにプロンプトを送信
2. Model Armor が受信プロンプトを検査(問題があればブロック/サニタイズ)
3. プロンプト(またはサニタイズ済みプロンプト)を LLM に送信
4. LLM がレスポンスを生成
5. Model Armor がレスポンスを検査
6. レスポンス(またはサニタイズ済み)をユーザーに返却。どのフィルタがトリガーされたかの詳細も返す

→ **入力(プロンプト)と出力(レスポンス)の双方向をフィルタリング**する点が要点。

### 2.3 フィルタの種類

**(1) 責任ある AI の安全フィルタ**
- カテゴリ: ヘイトスピーチ / ハラスメント / 性的に露骨な表現 / 危険なコンテンツ。
- カテゴリごとに信頼度しきい値(高 / 中以上 / 低以上)を設定可能。
- CSAM(児童性的虐待コンテンツ)フィルタはデフォルト適用で無効化不可。

**(2) プロンプト インジェクション / ジェイルブレイク検出**
- 直接的・間接的の両方のプロンプト インジェクションに対応。テキストのほか URL・PDF などの入力もサポート。
- 検出時はプロンプト/レスポンスをブロック可能。

**(3) Sensitive Data Protection(SDP)連携**
- 機密データの検出・分類・匿名化を行う Google Cloud サービスを Model Armor 内で直接利用。
- 基本構成: クレジットカード番号、米国 SSN、金融口座番号、米国 ITIN、Google Cloud 認証情報、API キーなどの検査のみ。
- 高度な構成: SDP テンプレートを利用し、詳細な検出ルールと匿名化(トークン化・削除など)まで対応。既存の検査テンプレートを流用でき、他ワークロードと一貫性を保てる。

**(4) 悪意のある URL の検出**
- フィッシング・マルウェア配布などに使われる不正 URL を検出(プロンプト/レスポンス中の最初の 40 URL までスキャン)。

### 2.4 主要な構成概念

- **テンプレート(Template)**: フィルタとしきい値のセット。アプリケーションごとにスクリーニング方法をカスタマイズする単位。
- **信頼度(Confidence Level)**: 「不適切コンテンツが含まれる」とどの程度確信しているか。高 / 中以上 / 低以上 でトレードオフ(誤検出許容度)を調整。
- **適用タイプ(Enforcement Type)**:
  - 検査のみ(Inspect only): 違反を検査するがブロックしない(Cloud Logging 併用で可観測性を確保。段階導入に有効)。
  - 検査とブロック(Inspect and block): 違反リクエストをブロック。
- **フロア設定(Floor Settings)**: 組織 / フォルダ / プロジェクト レベルで、その配下の全テンプレートに対する**最低限の保護基準**を強制するガードレール。個別アプリの柔軟性(テンプレート)と全社統制(フロア)の 2 層構造。※フロア設定では SDP は適用不可。

### 2.5 対応範囲・制限

- **多言語対応**: 日本語を含む 9 言語(中・英・仏・独・伊・日・韓・葡・西)でテスト済み。リクエスト単位またはテンプレート単位で多言語検出を有効化。
- **ドキュメント スクリーニング**: PDF / CSV / TXT / Word / PowerPoint / Excel 系ファイル内テキストを検査可能(入力サイズ上限 4 MB)。
- **トークン上限**: プロンプト インジェクション検出・責任ある AI・CSAM は 10,000 トークン、SDP は最大 130,000 トークン。超過時は EXECUTION_SKIPPED 等の挙動になる点に運用上注意。

### 2.6 統合ポイント(どこに差し込めるか)

- **REST API / クライアント ライブラリ**: アプリから直接 sanitize を呼ぶ(モデル非依存で最も汎用的)。
- **Gemini Enterprise Agent Platform / Agent Gateway**: ゲートウェイで Model Armor を構成し、エージェントの入出力を一括検査。スパン(トレース)やコンテンツ セキュリティのモニタリングも提供。
- **Vertex AI(Gemini API)**: フロア設定またはテンプレートで generateContent のリクエスト/レスポンスをインライン検査。
- **Gemini Enterprise(旧 Agentspace)**: ユーザー⇔エージェント⇔LLM 間のやり取りをテンプレート経由でルーティングして検査。
- **Apigee**: API プロキシに Model Armor ポリシーを組み込み、API ゲートウェイ層で検査(トークン クォータ等の API 管理機能と併用可)。
- **GKE Inference Gateway / Service Extensions(ロードバランサ)**: 推論ゲートウェイや ALB のトラフィックにインラインで安全性チェックを適用。
- **Security Command Center 連携**: 違反はセキュリティ検出結果(Findings)として集約され、モニタリング・アラート・修復のワークフローに乗せられる。監査ログ(Cloud Audit Logs)・Cloud Logging にも対応。

### 2.7 ユースケース

- IP・PII がプロンプト/レスポンスに混入して漏えいするリスクの低減。
- プロンプト インジェクション / ジェイルブレイクによる AI システム操作の防止。
- アップロード PDF 等に仕込まれた不正コンテンツ・不正 URL の検査。
- ブランド保護(不適切・有害コンテンツの生成防止、生成 SNS 投稿のフィルタリングなど)。

### 2.8 料金

- Security Command Center の一部として、またはスタンドアロン サービスとして購入可能。課金は処理トークン数ベース(詳細は SCC 料金ページを参照)。

## 3. 2 サービスの関係と運用上の位置づけ

- **役割分担**: Memory Bank は「エージェントを賢く・パーソナルにする」コンテキスト管理、Model Armor は「エージェントを安全に運用する」入出力ガードレール。両者は補完関係。
- **直接の接点**: Memory Bank 公式ドキュメントは、メモリ ポイズニング対策として「Memory Bank に出入りするプロンプトを Model Armor で検査する」ことを明示的に推奨。長期記憶は一度汚染されると影響がセッションを超えて持続するため、記憶に書き込まれる前の検査が特に重要。
- **運用の型(例)**:
  1. Agent Gateway / アプリ層で Model Armor により入力を検査(インジェクション・PII 除去)。
  2. クリーンな会話のみを Sessions に蓄積し、Memory Bank が記憶を生成。
  3. 記憶の取得結果を含むレスポンスも Model Armor で出口検査。
  4. 組織全体はフロア設定で最低基準を強制し、違反は SCC でモニタリング。
- **ガバナンス**: どちらも IAM(Memory Bank は IAM Conditions によるスコープ単位の制御)、CMEK / VPC-SC(Memory Bank)、監査ログ・Cloud Logging(Model Armor)といったエンタープライズ統制に対応。
